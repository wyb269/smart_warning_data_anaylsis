# 防返贫数据展示与智能预警平台：项目总结

项目围绕防返贫业务中的多源人员数据，建设了集中式 Hive 数据加工链路、自动预警规则与面向工作人员的数据展示平台。本文总结业务目标、技术架构、源表到报表的加工过程、页面设计和验收方法。仓库集中展示项目文档与 Pencil 原型，生产数据、连接凭据和系统源码保存在各自的受控环境中。

## 1. 业务问题与项目目标

外部部门的医疗、民政、就业、住房等信息先进入公司数据仓。原始数据按部门和事件分散存储，工作人员难以直接回答“某个人的必要信息是否齐全、哪些指标触发预警、依据是什么”。项目把同一人员的授权数据整合为可查的记录，并用经确认的规则自动计算预警。

从数学视角，每人的展示记录是 `x_p=(地区、身份、户主、有效性、农村户籍、10项指标、来源与时间)`；经确认的规则集 `R` 对可判断的指标计算 `W_p=R(x_p)`。产品同时展示 `x_p` 和 `W_p`，让用户看到结果及其证据。项目以缩短查找、理解字段和核对依据的时间为目标，并把数据覆盖与判断质量纳入效果评价。

项目交付的业务能力是**数据展示与自动初筛**：数据总览、人员清单、人员详情、智能预警、数据状态。正式监测对象认定仍走既有业务制度；平台页面没有责任人、办理状态、可见编号或逐人“人工判断”按钮。

## 2. 技术架构与各组件职责

| 环节 | 技术手段 | 具体职责 |
| --- | --- | --- |
| 上游数据接入 | 公司数据接入流程与集中式 Hive 仓库 | 接收授权源数据，保留来源、批次和所属期；项目团队通过公司数据仓使用数据 |
| 仓内加工 | Hive SQL 与批次任务调度 | 清洗格式、统一人员与地区、跨批去重、计算指标、产出报表层 |
| 应用查询 | HiveServer2/JDBC 与 MySQL 查询库 | Hive 承担批量加工与溯源；最小化展示结果同步至 MySQL，支撑人员筛选、分页和详情查询，不复制原始部门表 |
| 服务接口 | Java Spring Boot 与只读 REST API | 身份和数据范围校验、五级地区筛选、分页、统一口径、脱敏与访问审计 |
| 用户界面 | Vue 3 与 ECharts | 呈现五个原型画框对应的页面、筛选、指标分布和来源状态；图表均可追到人员数据 |
| 安全运维 | 公司既有身份认证、最小权限、日志与监控 | 对个人数据的访问授权、脱敏、留痕、批次失败告警和规则版本回滚 |

集中式 Hive 是主数据仓，批次任务在仓内运行；MySQL 保存页面交互所需的最小化派生结果；Spring Boot 提供授权查询接口；Vue 3 与 ECharts 呈现报表和人员详情。底层计算由公司仓库环境承载，项目团队通过授权的 Hive 服务和应用接口使用数据。

这一分工把批量处理和交互查询分开：Hive 将多来源记录加工成稳定的人员与指标结果；MySQL 按筛选条件快速返回少量页面数据。同步任务只传输授权的报表字段与汇总结果，避免应用端读取整套部门源表。

## 3. 从源表到报表：数据处理全过程

**源表不是被“改写成”报表。**源表保留原始业务含义和追溯能力；整合表、指标结果和页面报表是按规则计算出的派生数据。处理过程分四层：

| 层次 | 核心数据对象 | 粒度与处理动作 | 产出用途 |
| --- | --- | --- | --- |
| 源表层（ODS） | 各部门授权源记录 | 保留来源批次、数据所属期、接收时间，不在此层把空值判为“否” | 回溯原始证据和重算 |
| 标准明细层（DWD） | 人员主记录、医疗/救助/身份等事件 | 统一字段类型、行政区编码、时间；以受保护的内部人员键匹配同一人，以事件键去重 | 解决同名、重复、跨表关联问题 |
| 指标汇总层（DWS） | 一人一批的基础判断与逐指标结果 | 依据已确认时间窗口、阈值和“新增”基准计算 K–V；每项保留值、来源、业务时间、可用时间、规则版本与未知原因 | 形成可解释的预警输入 |
| 报表服务层（ADS） | 人员清单/详情、预警列表、总览、来源状态 | 按授权范围生成页面可查视图及汇总，统一去重口径 | 供平台接口读取 |

源数据进入仓库后的关键步骤如下：

1. **核对接入范围**：记录各来源的覆盖区域、人群、周期和最近可用时间。只对已授权、已交付数据做处理。
2. **清洗与匹配**：把省、市、县、乡、村统一到可解释的五级字段；证件号等敏感匹配值仅在授权计算环境内使用。户主关联缺乏可靠依据时保持空值。
3. **质量检查**：检查字段缺失、跨批重复、人员无法匹配、来源冲突和更新延迟；问题写入数据状态，不悄悄补成“否”或 0。
4. **计算指标**：基础判断 K“人员有效性”和 L“是否农村户籍”与 10 项预警指标 M–V 分开处理。医疗自付是否超万元按确认的统计期间和累计口径判断；临时救助按确认的近三个月窗口；“新增”类指标要有可比较的基线。失业金发放记录不能直接等同于当前失业，危房改造计划不能直接等同于现存危房。
5. **生成报表**：按内部人员键形成一人一份整合详情，另形成一人多指标的证据记录，以及按地区和时间汇总的统计结果。
6. **定期更新与重算**：按批次增量处理；同一人同一事件重复送达时更新证据而不重复计数。规则变更使用新版本重算，并能回溯旧版本结果。

指标状态集合为 `S={命中, 确认未命中, 无法判断, 未接入}`。仅当来源覆盖、人员匹配、时效和规则都满足判断条件时，才可把未触发写成“确认未命中”。“无法判断”需附缺批、未匹配、字段缺失或冲突等原因。统计分母使用**已交付且可匹配的人群**，不计算全域农户风险率。

## 4. 字段与规则如何落到页面

原型的字段基线来自《整合表》：B–F 为省、市（地区）、县（市、区）、乡（镇）、村（社区）；G–H 为人员姓名与证件号；I–J 为可空的户主信息；K–L 为人员有效性和农村户籍；M–V 依次为个人医疗自付是否超万元、是否启动大病保险、是否新增残疾人员、是否新增低保人员、是否新增特困人员、三个月内是否为临时救助对象、是否新纳入低保边缘人员、是否新纳入支出困难人员、是否失业人员、是否有危房。A 列原表序号不在业务页面展示。

每项指标至少有 `结果 + 具体值/档位 + 业务时间 + 来源 + 最近可用时间 + 规则版本/状态`。来源没提供精确金额时只显示已交付档位，不编造金额。规则是否启用、阈值、统计窗口和“新增”的比较点均以业务签字版本为准。

页面与报表层按同一口径关联：

| 页面 | 读取的报表结果 | 用户能完成的动作 |
| --- | --- | --- |
| 数据总览 | 人员去重数、命中人员数、指标命中次数、数据待补数、地区分布 | 了解数据覆盖与趋势，点击数字回到对应清单 |
| 人员数据 | 授权人员整合记录 | 用省、市、县、乡、村及姓名/证件号后四位筛选，查看某人详情 |
| 人员详情 | B–V 必要字段与逐指标证据 | 看具体数据、来源、时间、命中原因和“无法判断”原因 |
| 智能预警 | 经已启用规则自动筛出的命中视图 | 按地区、指标和时间过滤，进入同一人员详情 |
| 数据状态 | 来源接入、覆盖、所属期、延迟、匹配与缺失结果 | 判断当前页面数据是否足以支持解释 |

一人可命中多项：**命中人员数**按内部人员键去重，**指标命中次数**按人和指标计数。两者不能混用。总览、人员清单、预警列表在相同地区和时间筛选下应可对账。

## 5. 典型查询与处理链路

以“查看某村最近一批的预警人员”为例：

```text
用户选择省→市→县→乡→村
  → 服务端验证该用户可见的地区与字段
  → 从报表服务层读取分页人员及预警摘要
  → 用户点击“查看”
  → 按内部人员键读取 B–V 字段、逐项证据、来源时间与规则版本
  → 记录详情访问审计（不记录敏感正文）
```

预警是批量规则的输出，不要求工作人员逐条提交判断。工作人员仍可依据现有业务制度对正式认定、数据异议或规则修订作业务处理；这些流程不属于本版平台页面。

## 6. 验收与效果评价

项目围绕字段完整性、规则可复现性、跨页面统计一致性、安全控制、查询性能和来源时效六个方面组织验收。

| 目标 | 验证方式 |
| --- | --- |
| 字段展示完整 | 对照《整合表》B–V 逐项检查人员详情，确认五级地址、可空户主、2 项基础判断和 10 项指标均有位置和明确状态 |
| 规则可复现 | 用脱敏或合成样例验证命中、未命中、缺批、未匹配、未接入、跨批重复、规则变更；结果能追溯到来源与版本 |
| 统计一致 | 相同筛选条件下，对账总览人数、清单人数和预警去重人数；区分人数与命中次数 |
| 安全可控 | 验证账号授权、地区范围、证件号脱敏、详情访问审计及默认禁止个人明细导出 |
| 性能达标 | 在公司授权环境和约定数据量下测量清单与详情查询的 95% 响应时间，以 3 秒内为目标保存压测记录 |
| 来源可解释 | 对每个来源检查接入、延迟、缺失、覆盖范围和最近可用时间；缺批不画成真实的零 |

业务效果以“查找 + 理解 + 核对”三段时间、字段可用率、无法判断比例和错误预警纠正率衡量。项目总结记录方法与口径，不使用缺少统计依据的改善幅度。

## 7. 项目成果与复盘

| 成果 | 实施结果 |
| --- | --- |
| 人员数据整合 | 将分散的授权源记录按内部人员键关联，形成包含五级地区、身份、户主、基础判断和十项指标的人员视图 |
| 自动预警计算 | 依据版本化规则批量生成命中结果与逐项证据；缺批和冲突进入无法判断，不以缺失代替未命中 |
| 报表展示 | 形成总览、人员清单与详情、预警清单和数据状态四类报表，支持地区、指标和时间筛选 |
| 质量与安全 | 保留来源批次和可用时间，统一统计口径；页面按授权范围查询，证件号脱敏，详情访问留痕 |

项目的关键经验是先定义**数据粒度、人员匹配依据、来源覆盖和规则版本**，再做预警统计。源表记录数、去重人员数和指标命中次数属于不同度量；把它们混用会使地区分布和预警人数失真。数据质量状态与业务指标同样重要，因为“无法判断”代表证据不足，并不代表风险不存在。

仓库只保存项目文档和合成示例原型；生产连接串、账号、令牌、完整证件号、医疗明细和客户原始资料保存在受控系统中。
